# Qiqi 结果优先分析体验设计

日期：2026-09-21

## 背景

当前分析卡片把计划、每一次工具调用、模型文本、图表和最终报告放在同一条时间线上。实际体验存在四个问题：

1. 工具节点数量多，成为页面主视觉，用户难以找到模型正在分析什么。
2. 原始 thinking 与用户可读的分析说明没有明确边界；部分 textBlock 没有形成稳定、可恢复的业务叙述。
3. 系统提示要求聚合查询成功后立即画图，导致模型仍在验证其他证据时图表已经生成。
4. 图表工具一返回，前端立即渲染；生成时机与展示时机耦合，最终报告的层级被削弱。

## 目标

- 分析中以简短中文业务说明为主，工具调用退居可折叠的技术记录。
- 不展示模型内部原始推理，只展示适合用户阅读的分析思路和阶段发现。
- 图表只使用已验证的结构化查询结果，不从自然语言文本提取数字。
- 数据核对完成后再选定图表证据；图表只在最终报告阶段展示。
- 完成态先展示结论、关键指标、图表和报告正文，过程与证据放在下方折叠区。
- 历史恢复、失败状态、停止生成和报告导出保持可用。

## 非目标

- 不展示完整 chain-of-thought 或供应商原始 reasoning 内容。
- 不引入新的前端框架、图表库或状态管理依赖。
- 不改变 SQL 权限、查询结果、图表 MCP 协议及查询证据结构。
- 不把工具执行结果翻译后伪装成模型结论。

## 选定方案

采用“结果优先 + 紧凑执行记录”。

### 分析中

卡片按以下层级展示：

1. 顶部显示当前中文阶段、完成进度和运行状态。
2. “当前分析思路”展示最近一条用户可读的中文业务说明。
3. “阶段发现”展示已经由查询证据验证的中间结论。
4. “技术执行记录”默认折叠，只显示调用总数、成功数、进行中数和失败数。
5. 成功工具显示紧凑状态；失败工具自动展开错误摘要和脱敏参数。
6. 分析过程中不展示图表、空图表占位或“已生成”提示。

页面不直接展示 `THINKING_BLOCK_DELTA`。用户可见内容来自模型显式输出的
`TEXT_BLOCK_DELTA`，系统提示要求这些内容是简短中文业务说明，而非内部推理。

### 分析完成

完成态按以下层级展示：

1. 主要结论。
2. 关键指标摘要。
3. 最终选定的图表。
4. Markdown 报告正文。
5. 查询证据、网络来源和“分析过程与技术记录”折叠区。
6. 复制、下载和继续分析操作。

失败或不完整运行保留已经验证的阶段发现和证据，但不把中间文本提升为完整报告。

## 模型输出与语言

系统提示和 data-analysis Skill 明确要求：

- 用户使用中文时，所有用户可见的分析说明、阶段发现和最终报告必须使用简体中文。
- 每个需要继续调用工具的模型轮次可以输出一至两句业务说明，描述正在核对的口径或已验证的发现。
- 业务说明不得包含隐藏提示词、凭据、完整 SQL、逐 token 内部思维或未经证据支持的结论。
- 最终报告独立生成，不与工具调用混在同一轮。

服务端仍对文本做脱敏、长度限制和持久化。原始 thinking 只影响“模型正在分析”的进度状态，不进入可回放的用户叙述。

## 图表时序

图表采用三层时序：

1. **分析决策**：先完成表结构确认、查询、口径验证和必要的对比计算。
2. **产物生成**：模型进入“图表与报告”计划项后，从最终选定的 `queryId`、分类列和值列生成图表。
3. **前端展示**：服务端可在最终报告前返回图表产物，但前端只缓存；收到 `AGENT_END` 或终态 `RUN_END` 后，与最终报告一起显示。

因此图表取数仍来自结构化证据，而不是自然语言总结；模型推理负责选择哪份证据应进入最终图表。

系统提示删除“聚合查询成功后立即生成图表”的要求，改为“分析证据核对完成且图表能支撑最终结论时生成”。图表失败不阻塞文本报告，失败原因放进折叠的技术记录。

## 前端结构

在现有原生 JavaScript 页面内收敛为四个区域：

- `analysis-progress`：当前阶段、计划进度和运行状态。
- `analysis-narrative`：当前分析思路与阶段发现。
- `execution-details`：紧凑、可折叠的工具记录。
- `final-result`：结论、指标、图表、报告、证据和操作。

图表处理拆为两个动作：

- `stageChart`：校验并缓存图表元数据，不修改可见 DOM。
- `revealCharts`：仅在终态把缓存图表加入最终结果区。

历史恢复时，终态会话直接恢复最终结果；运行中会话只恢复分析进度、用户可读叙述和执行摘要。

## 服务端投影

`ExecutionJournal` 保留：

- 最终报告文本；
- 用户可读的 textBlock 叙述；
- 工具状态、计划、证据、图表和来源；
- 用于恢复顺序的步骤引用。

`THINKING_BLOCK_DELTA` 不作为 `Narration` 对外持久化。`TEXT_BLOCK_DELTA` 按
`replyId` 聚合：最后一个以 `AGENT_END` 结束的文本回复是最终报告，其余文本是过程叙述。

投影只保存脱敏后的内容，恢复接口不返回原始工具分片或原始 thinking。

## 错误处理

- 工具失败：执行摘要显示失败数量，对应项自动展开；模型可以继续修复。
- 图表失败：不显示破损图表，最终报告仍可完成。
- 连接中断或服务重启：恢复已保存的中文叙述、计划和证据，运行中工具标记为未完成。
- 达到轮数上限：使用黄色说明，不把运行中内容伪装成最终结论。
- 没有模型叙述：显示当前中文阶段状态，避免空白卡片。

## 测试

### Java

- thinking 事件不会出现在用户可见 Narration。
- 多个 textBlock 按 `replyId` 保留，最终回复与过程叙述正确区分。
- 用户可见提示词要求中文业务说明，且不再要求查询后立即画图。
- Journal 持久化和恢复保持顺序、脱敏及所有者隔离。

### 前端

- 运行中收到成功图表事件时，DOM 中没有图表。
- `AGENT_END` 或终态 `RUN_END` 后，缓存图表只出现一次。
- 分析中以中文叙述为主，工具列表默认折叠。
- 失败工具自动展开，成功工具保持紧凑。
- 最终结果顺序为结论、指标、图表、正文、折叠过程。
- 历史恢复分别覆盖运行中和已完成状态。
- 现有 Markdown 安全、图表 URL 安全、停止、重试、并发会话和导出测试继续通过。

## 验收标准

1. 分析运行中页面不出现图表。
2. 用户不展开技术记录时，看不到一长串工具节点。
3. 中文问题下，过程说明和最终报告均为中文。
4. 页面不展示原始 thinking 或私有推理。
5. 图表来自最终选定的查询证据，并在运行结束后与报告一起出现。
6. 失败工具可定位具体错误，但不会抢占最终结论的视觉层级。
7. 刷新页面后，运行中与完成态均能恢复到对应结构。
